## 更正（推翻上一节的两条结论，以本节为准）

上一节「镜像救不了」与「21.11.41 只是没缓存」都是错的：

1. **21.11.41 从未发布成制品**。用能实时回源的 creeperhost 复核：`neoforge-21.11.41.pom` → **404**，而 `21.11.42 / .44 / .45 / .48` 全部 **200**。所以那个 404 是「上游本来就没有」，不是缓存缺失。教训：**见到 404 要先用实时回源代理复核，再下结论**。
2. **镜像是可用的**。creeperhost 是 maven.neoforged.net 的**实时回源代理**，工具链齐全：单独建了个最小 Gradle 工程解析 `net.neoforged:neoform-runtime:2.0.5`，连带 picocli / problems-api / gson / ecj / fabric-loom-native / srgutils 全部成功。

**镜像实测覆盖面**

| 镜像 | 结论 |
|---|---|
| `https://maven.creeperhost.net` | 实时回源，**最可靠**，工具链 + 制品齐全 |
| `https://mirror.sjtu.edu.cn/bmclapi`（BMCLAPI/SJTU） | 国内快但**残缺**：无 `neoform-runtime`，`neoform/1.21.11-*` 只有 mappings，部分版本夹缺件；有可浏览目录索引，适合核查「某版本到底有没有」 |
| `https://bmclapi2.bangbang93.com/maven/` | 仅部分快照，不可依赖 |

**两个必须记住的坑**

- **Gradle 的「缺失模块」缓存会毒化后续构建**：第一次没配镜像而失败后，即使补上镜像也仍报同一个错，必须加 `--refresh-dependencies` 才能恢复。
- 镜像的 404 与「上游不存在」要分开判断，方法就是用实时回源代理交叉验证。

**最终 pin**：`neo_version=21.11.48`（BMCLAPI 上有缓存的最新 21.11 补丁）；要与原始目标最接近可用 `21.11.42`。

## 编译终于通过（本节为最终状态）

`./gradlew build` → **BUILD SUCCESSFUL**，产出 `build/libs/getskeeper-1.0.0.jar`（166 KB，74 个 class + 全部资源）。这是本日最关键的进展，也修正了此前「无法编译验证」的结论。

**报错链的四个真实关卡（按出现顺序）**

1. `:neoFormRuntimeExternalTools` 拉 `neoform-runtime` 超时 → MDG 在 `plugins {}` 阶段就把官方仓库注册进列表，**位置早于** `build.gradle` 的 `repositories` 块；Gradle 遇 **404 会跳到下一个仓库，遇超时会中止**，所以「另加镜像」无效，**必须改写仓库 URL 本身**（`repositories.all { }` 里 `setUrl`）。
2. `neoforge → neoform → net.neoforged:minecraft-dependencies:1.21.11` 只在官方 `/mojang-meta/` 上。BMCLAPI 无此路径；creeperhost 只代理了 `/releases/` 与 `/snapshots/`（列出 nexus 全部 29 个仓库确认过）。**该制品承载 MC 全部库依赖**，缺了会报 96 个 `com.mojang.serialization / io.netty.buffer 不存在`（配置名是 `neoFormRuntimeDependenciesRuntimeClasspath` 与 mod 的 `minecraft` 配置，所以不能靠 exclude 绕）。
   → 解法：`tools/generate-minecraft-dependencies.py` 从 NFRT 已缓存的 MC 版本清单重建等价模块（107 项去掉 natives 分类器 = 51 条依赖），落到 `gradle/local-repo`，再把 `Mojang Meta` 仓库重定向过去。`libraries.minecraft.net` 可达，库本身没问题。
3. NFRT 的 recompile 会直接从 `maven.neoforged.net/releases` 补下个别库（当时是 `error_prone_annotations-2.41.0.jar`）。NFRT 缓存布局是 `~/.gradle/caches/neoformruntime/artifacts/<group>/<artifact>/<version>/`，**把文件放进去即可，它只看文件在不在**；中央仓库有的就直接从那取。
4. `generateModMetadata` 的 Groovy 模板报 `Unexpected input: '('` —— 元凶是**注释里写了字面量 `${...}`**，Groovy 会把它当表达式求值。官方模板的注释里不含花括号占位符，这就是原因。

**改对的地方（真实签名，已由编译器背书）**

- `PacketDistributor` 只有服务端发送方法；客户端发包要用 `net.neoforged.neoforge.client.network.ClientPacketDistributor#sendToServer`。
- 在 record 内调用外层类的**同名静态工厂**必须限定名（`GKPayloads.type(...)`），否则被 record 自己的 `type()` 覆盖。
- `ByteBuf`（netty 4.2）**没有** `writeVarInt/readVarInt`，用 `writeInt/readInt`。
- netty 4.2 / MC 1.21.11：`AbstractArrow.getPickupItemStackOrigin()` 是 **public**，而 `getPickupItem()` 与 `isInGround()` 是 **protected**（用 `javap -p` 反汇编 + 映射表把混淆名对应起来才确认）。所以静止判定改为 `isNoPhysics() || onGround() || getDeltaMovement().lengthSqr() < 1e-4`，不要 AT/mixin。
- `BuiltInRegistries.ITEM.getOptional(id)` 返回 `Optional<Item>`，不带 `.value()`。
- 同一包内的类要写全 `MacTheme.paragraphHeight(...)`，`JavaCompile` 不会自动 static import。

**方法论要点（本轮最有复用价值的一条）**：**DNS 全源污染时，`/etc/hosts` 这条路是死的**。实测腾讯 DoH（doh.pub / dnspod）返回 `208.43.170.231`，阿里 DoH 与 360 DoH 返回的却是 Facebook 段（`66.220.148.145` / `31.13.95.18`）——**不同 DoH 会给出不同（被注入的）答案**，且候选 IP 的 443 全部 TCP 超时。所以只能改走「改仓库 URL + 本地重建制品 + 预置缓存」三层。

## 运行时验证：编译通过 ≠ 能跑（重要）

编译通过后我**真的启动了一次开发服务端**，立刻抓到一个编译期查不出的崩溃：

```
Caught exception during RegisterEvent dispatch for modid getskeeper
java.lang.NullPointerException: Item id not set
  at net.minecraft.world.item.Item$Properties.effectiveDescriptionId(Item.java:673)
```

**根因**：`Item.Properties` 现在自带物品 id。若用 `DeferredRegister.Items.register(name, Supplier)` 自己在 supplier 里 `new Item.Properties()`，id 就是空的。必须用**带 key 的工厂**让 NeoForge 注入：
```java
ITEMS.register("mounted_container_image",
        key -> new MountedContainerImageItem(new Item.Properties().stacksTo(1)
                .setId(ResourceKey.create(Registries.ITEM, key))));
```
（也可用 `registerItem(name, Function<Item.Properties, I>, Supplier<Item.Properties>)`，它内部做同样的事。）

**服务端验证的做法（可复用）**
- `run/eula.txt` 写 `eula=true`；`run/server.properties` 里改端口（本机 25565 有用户自己的进程，别去动）。
- **Gradle 不转发 stdin**：用管道给 `runServer` 喂命令是无效的（试过 FIFO，命令进不去）。
  要下发命令就开 RCON：`enable-rcon=true / rcon.port=25600 / rcon.password=...`，再用一个最小 RCON 客户端（TCP，`<len><id><type><body>\0\0`）。
- 日志会被 `logLevel = DEBUG` 撑到 2 万行，用 `awk '/Done \(0\./{f=1} f'` 只看启动之后的部分。

**验证结论（均已实测通过）**：服务端 `Done (0.115s)!` 正常起来；`GetsKeeper: Trust lists loaded: 1 fully trusted, 0 trusted, 0 blocked`；`run/config/getskeeper-common.toml` 正常生成；物品/附件注册无异常。

对照：`help nosuchcommand` → `Unknown command or insufficient permissions`（未注册的对照），`help give` → 正常打印用法，说明 `help passwd` 返回空只是「裸 literal 无子节点」的显示特性，`/passwd` 确实已注册。

## 密码"填什么都不通过"——根因与修法（用户自查确认）

用户反馈「设置初始密码无论填什么都校验未通过」。排查过程与结论：

- 先用临时命令探针在真服务器上验证数据层，**全部正常**：`GKWorldData.get()` 非 null、`setPassword`/`hasPassword`/`verify(ok)=true`/`verify(bad)=false`、`minLength=6`、`iterations=120000`。所以不是存档、不是哈希、不是附件。
- **真正原因**：`security.min_length` 默认 **6**，而 UI 完全没有提示，且"太短"与"密码错误"共用同一条 `getskeeper.password.rejected`，所以看起来像"填什么都不对"。——`PasswordService.store` 的三条 `return false` 里，**长度不足**是最容易被误判成密码错误的那条。
- 修法（已落地）：`PasswordPrompt` 载荷新增 `minLength`，**由服务端把策略随提示一起下发**（客户端不去读自己的 config，避免两端不一致时又变成谜之拒绝）；`PasswordScreen` 在标签上直接写明「密码（至少 N 位）」，并在"设置新密码"时提前拦截过短的输入，给出专用文案 `password.too_short`；服务端 `store` 的每条拒绝原因都写日志。
- 顺带修掉一个布局 bug：错误行原本画在 `panelY + panelHeight - 52`，正好压在密码输入框上（字段 122..142 vs 错误 138）。已重排为固定行距（PANEL_HEIGHT=200，错误在相对 148）。
- 协议版本从 `1` 提升到 `2`：载荷字段变了必须升版，否则新旧构建的客户端/服务端会互相误读。

**教训（值得记住）**：这类"策略存在于配置里但界面不表达"的缺陷，编译器查不出、服务端探针也查不出（因为服务端行为完全正确），**只有真正看界面才会发现**。在没有图形会话的环境里，遇到"用户说 UI 行为不对"时，优先怀疑"策略未被表达"，而不是继续深挖后端逻辑。

## 用户报告的 7 个 BUG：根因与修法

用户实测后发现 7 个问题，全部修好（提交见当日最后一次 commit）。根因按"设计意图没落地"归类：

1. **授权不被记录 + 完全信任陷入死循环**（一个 BUG 的两半）
   - `UseGuard.handleDecision(CONTINUE)` 根本没调 `AuthorizationService.authorize` —— 规格 7.1 明确要求"点继续即授权"，所以授权永远写不进去，同一件物品每次使用都重新走验证。
   - `UseGuard.resolve` 的 `passesSilently()`（完全信任）分支调了 `reapply` 但**没有清 `SNAPSHOTS` 基线**，下一个 tick 把刚放回去的物品当成"新变化"，再拦一次 → 无限循环。（`handleDecision` 有清，`resolve` 漏了。）
2. **除密码弹窗外按钮点击不关闭**：`MacDialogScreen.layoutButtons` 直接把 `choice.action()` 交给按钮，动作自己不关界面；`PasswordScreen` 的按钮恰好自己调了 `onClose()` 所以只有它正常。现在统一由 `choose(choice)` 包一层：跑动作 + 关闭，且只执行一次。
3. **Esc 关闭不计作按钮、物品不返还**：根因有两层。
   - 弹窗层：改由 `onClose()` 走"安全选项"（非破坏性那个），并删掉重复语义的 `Builder.onDismiss`。同时**弃用 `pushGuiLayer`**：背包满警告改为普通 `setScreen` 替换拾取界面，一次确认即全部关闭。
   - **真正的数据丢失在 `UseGuard`**：守卫的"撤销"只把被监视槽位写回旧内容，**没有把被移动的堆叠还回去**，所以拦截一旦取消，物品就凭空消失（交换时还会复制另一件）。现在**整背包快照 + 整背包回滚**（移动有两端，只回滚一端必然丢/复制），并且 `CANCEL` 会把堆叠放回背包（满了才掉落）。
4. **本模组物品不应被处理**：`UseGuard.isTrusted`、`PickupInterceptor.isOfferable`、`SourceRecorder.isRecordable` 三处都排除 `MountedContainerImageItem`。
5. **映像丢弃后仍存在**：`onDroppedByPlayer` 返回 `false` 会**取消丢弃**，物品留在原槽位——正是用户看到的现象。正确做法是允许丢弃、并**阻止实体进入世界**（`EntityJoinLevelEvent` cancel）：此时原版已把堆叠从背包取出，拒绝实体本身就是销毁。删除该覆写，新增 `item/MountedImageGuard.java`，顺带补上规格里有但一直没实现的"死亡不掉落 + 死亡后在重生玩家身上保留"（`LivingDropsEvent` 过滤 + `PlayerEvent.Clone` 复制）。
6. **玩家丢出的物品被当成待拾取**：`ItemEntity.hasPickUpDelay()`（public）为真时跳过——原版自己也有这个宽限期。另外把 `setCanPickup(FALSE)` **挪到 `offer()` 成功之后**：原来先否决再 offer，若 offer 没开出界面，物品就被卡在地上谁也捡不走。
7. **隐私页底部列表**：删掉标题与空状态文案，列表为空时整块不绘制；`privacy.blocked_header` / `privacy.blocked_empty` 两个 key 从两种语言里一并删除。

**i18n 自检脚本**（值得保留的做法）：用正则扫 `src/main/java` 里的 `"getskeeper.*"` 字面量，与两种语言的 key 集合做双向差集，能同时发现"代码用了但没定义"和"定义了但没人用"。注意两个预期误报：`argument.item.id.invalid` 是原版 key；`getskeeper.source.` 是代码里动态拼接的前缀。

## 用户报告的 10 个新 BUG（第二轮实测）

按用户实测清单修完，含上一轮未提交的两项（拾取拦截、快捷栏切换）。**根因归类**：

**验证状态机（4 项）**
- #4「按 F 交换副手 → 取消后物品复制」：**F 交换走的是可取消的 `LivingSwapItemsEvent.Hands`**（vanilla 在
  `ServerGamePacketListenerImpl` 里先问事件再 `setItemInHand`）。之前只靠 tick 守卫事后撤销再复现，撤销与
  "把栈写回监视槽"叠加就复制。改为**在事件里直接拒绝**（无需撤销 → 不可能复制），CONTINUE 时用footprint 执行交换。
- #5「完全信任物品仍触发验证」+ #3「完全信任的进度条不消失」：`isTrusted()` 只查了玩家授权记录，**没查信任等级**，
  于是 `FULLY_TRUSTED` 也走完整验证（进度条 + 首次使用被丢弃）。现在 `isTrusted` 把 `passesSilently()` 当作免检，
  另外 `resolve` 的静默分支补发 verdict（否则客户端进度条永不结束）。
- #9「左键破坏没拦截」：破坏不走 use-on-block / use-item，新增 `PlayerInteractEvent.LeftClickBlock`（START）拦截。
  注意**创造模式无效**：vanilla 在该模式下不查此事件。
- **撤销/复现模型整体重做**（这是本轮最大的改动，见下"方法论"）。

**界面（3 项）**
- #2「进度条不能覆盖背包」：vanilla 的渲染顺序是 **HUD 先、界面后**，NeoForge 的 `drawScreen` 还会把注册的 GUI 层
  画在界面**更早**。所以单靠 GuiLayer 永远在界面之下 → 增加 `ScreenEvent.Render.Post` 再画一遍（HUD 层在界面打开时跳过）。
- #7「自定义 UI 文字不要阴影」：`MacTheme.text/paragraph` 本来就 `shadow=false`，但 `MacTheme.centered` 与若干
  直接调用 `GuiGraphics#drawCenteredString`（那个重载**总是**带阴影）的地方没有 → 统一改成 shadowless 的 centered
  （新增 `FormattedCharSequence` 重载给 `font.split` 的行）。唯一保留阴影的是进度条标签（直接画在世界之上）。
- #10「拾取弹窗没有关闭键」+「Esc 后仍拾取」：加了 Close 按钮（`getskeeper.pickup.close`）；"Esc 后仍拾取"其实是
  上一轮那个"offer 失败就不否决"的漏洞在冷却期内被 vanilla 拾走 → 已在上一轮修复（否决先行）。

**隐私页 / 文案（3 项）**
- #1「授权后条目不消失」：`SessionGuards` 只有 `mark`，没有 `unmark` → 授权成功且记录已可用时移除并重发列表。
- #8「拉黑物品不该出现在仍要使用列表」：`resolve` 里原本 UNTRUSTED 与 BLOCKED 都 `mark`；BLOCKED 无法被授权，
  列出只会给一个没用的按钮 → 只 mark UNTRUSTED。
- #6 用户改的 `getskeeper.dialog.blocked.body` 现在是三参数（`%1$s` 玩家、`%2$s` 时间、`%3$s` 来源）：代码补上参数，
  并加 `blocked.body_no_source` 处理"无来源记录"（否则时间戳会是 1970）。`en_us` 同步成同一形状。

## 方法论：无图形环境下验证服务端状态机（本轮最有复用价值的一条）

**用 `FakePlayer` + 手动 post 事件 + RCON，可以真正跑出服务端状态机的结论**：

1. `FakePlayerFactory.getMinecraft(overworld)` 拿到的假玩家**自带 `FakePlayerNetHandler` 连接**，所以
   `PacketDistributor.sendToPlayer` 不会 NPE —— 这是整个方法能成立的关键。
2. 手动 `NeoForge.EVENT_BUS.post(new PlayerTickEvent.Post(fake))` 驱动 tick 逻辑；**世界时钟在同一 tick 内不动**，
   所以 `resolveAt` 不会到期，可以稳定地在"pending"状态下调用 `UseGuard.handleDecision` 做断言。
3. **观测量选"公开的决策 API 的副作用"**：CONTINUE 会写授权记录，所以 `AuthorizationService.record(fake).isUsable(id)`
   就是"刚才是否真的拦下了"的判据（没有 pending 时 handleDecision 直接返回，什么都不会变）。
4. **基线要显式清干净**：`UseGuard.resync(fake)` 清快照基线，然后再 tick 两次。否则"布置场景"这个动作本身
   （未授权物品进入受监视槽）会先被守卫拦下，断言测到的就是那个拦截而不是想测的东西 —— 这个坑我第一次就踩了
   （F 交换场景报 `refused=false`，实际是基线被污染）。
5. **命令行 spawn 的实体在同一 tick 内对 `getEntitiesOfClass` 不可见**（实体分区要等下一次 level tick），
   所以需要真实体的场景要**拆成两条命令**，中间 `sleep` 让服务端 tick 一次。
6. 测试环境靠**改 `run/config/getskeeper-common.toml`**（如把 `fully_trusted` 清空让所有物品都需要验证），
   而不是改代码。跑完记得改回去。

本轮实际结论（`gkprobe` 输出）：1 手内换物 verified=true；2 快捷栏切换 verified=true；3 新物品被扣住=true、
会话缓存物品放行=true、决策期间连缓存物品也被扣住=true；4 交付批次后 verified=false 且物品仍在（旧的会被撤销掉）；
6-1 F 交换被拒=true 且继续后手/副手互换、数量不变（3/5）；6-2 取消后双手原样（7/11）。
**箭矢场景仍未跑通**：假玩家不加载区块，命中的箭矢会被服务端清掉（`alive=false`），只能在真机上验。


## 第三轮：右键装备未被拦截 + 完全信任不显示进度条

**#1「装备右键使用未被拦截，并导致物品复制」**：缺的是 `PlayerInteractEvent.RightClickItem` —— vanilla 在
`ServerPlayerGameMode#useItem` 的**第一件事**就是 `CommonHooks.onItemRightClick(...)`，装备盔甲走的正是
`Item#use` → `Equippable#swapWithEquipmentSlot`（把物品从手移进装备槽）。这条路径既不过 use-on-block 也不过
use-item，所以之前只有 tick 守卫在**事后**看到它：物品已经穿上，撤销/复现还要碰 footprint，于是复制。
现在在事件里直接拒绝（返回 `InteractionResult.PASS`）→ 无撤销即无复制。

**#2「完全信任物品不会展示进度条」**：这是我上一轮的**过度修正** —— 我把 `isTrusted` 扩到包含
`passesSilently()`，于是 `FULLY_TRUSTED` 整个 pass 被跳过，进度条随之消失。用户的真实意图是
"进度条要在、但要会消失、且不重复"（对照上一轮 #3/#5 的措辞）。已还原：免检物品仍走 pass（进度条），
静默分支照旧发 verdict（进度条结束），基线照旧清掉（不循环）。

**顺带发现并修掉的过度拦截**：`UseItemOnBlockEvent` 对一次右键会触发三次（BEFORE_BLOCK / AFTER_BLOCK / BLOCK）。
BLOCK 阶段是"方块对右键的回应"（箱子/门/按钮），我们原来也拦 → 拿着未授权物品**打不开箱子**。
现在跳过 BLOCK 阶段；BEFORE_BLOCK 用 `PASS` 而非 `FAIL` 取消（vanilla 只有 PASS 才把回合交给方块）。

**实测（临时探针，跑完已删；测试配置 `fully_trusted = ["minecraft:bone"]`，其余物品都需验证）**：
7 右键装备 → `result=Pass[]`、头盔仍在手上、头上仍空、`intercepted=true` ✔（拦截生效、复制消失）
8 绕过事件直接装备 → 拦截时被撤销、继续后"头上=金头盔、手上=空、总数=1" ✔（不复制不丢失）
9 取消 → "手上=锁链头盔、头上=空、总数=1" ✔
10 箱子：拿着未授权头盔 → 返回值与"已授权对照"**完全一致**（都是 `Success[...]`），说明阶段过滤后方块交互不再被中止；
    但假玩家在这个环境里**开不了菜单**（对照同样 `opened=false`、`menu=InventoryMenu`）→ "箱子能打开"这句只能在真机上确认。
11 完全信任物品（bone）→ `pass started=true` ✔（进度条回来了）

## 第四轮：完全信任物品验证完成后仍无法使用

**根因**：`FULLY_TRUSTED` 只被"撤销 + 复现"那条路支持，而**所有在事件层被否决的"使用"都不可能被复现** ——
`reapply()` 见到 `slot < 0`（= 不是槽位移动）直接 return。于是完全信任物品的每次右键/装备/挖矿都是：
被否决 → 进度条播完 → 什么都不发生；玩家再试 → 再播一次 → 永远用不了。用户上一轮报的
"进度条结束后仍会触发验证"和这一轮的"验证完成后仍无法使用"是同一个 bug 的两面。

**修法（收敛到"播报式 pass"）**：新增 `needsAnswer(player, stack)` 作为**所有钩子的否决判据**：
- `isTrusted`（本模组物品 / 玩家已授权）→ 连 pass 都不起；
- `needsAnswer`（TRUSTED / UNTRUSTED / BLOCKED）→ 否决或撤销 + 进度条 + 弹窗；
- `FULLY_TRUSTED` → 两者都不占：**不否决、不撤销，操作照发生**，只播报进度条（新 `ANNOUNCED` map，
  `resolveAt` 到期后发 FULLY_TRUSTED verdict 让进度条落下）。

守卫里"完全信任物品落到手上/装备槽"的到货也走播报而不是撤销（`allowed` 与 `watched` 两条路分开），
所以装备不再闪一下又回到手上。`begin()` 里 `ANNOUNCED.remove(id)`：一次只能有一条进度条。

**实测（临时探针 + 真服务端，跑完已删；测试配置 `fully_trusted = ["minecraft:bone","minecraft:leather_helmet"]`）**：
1 完全信任右键 → `refused=false pending=false`，且进度条期间再点一次仍 `refused=false`（可用）；
2 完全信任头盔用 `fake.gameMode.useItem(...)` 走 vanilla 真路径 → `hand=empty head=leather_helmet`，
  再 tick 两次**没有被撤销**、`pending=false announced=true`（进度条播报）；
3 未授权苹果右键 → `refused=true pending=true`（对话路径未回归）；
4 挖矿 → `fullyTrustedRefused=false untrustedRefused=true`；
5 播报中的完全信任物品（快捷栏切换触发）→ 等真实世界时钟走过时长后 `announced=true → false`，
  再三 tick 仍 `false`（不自重启），随后右键 `refused=false`（过完进度条依然可用）。

**踩到的坑（值得记住）**：`runServer` 报的是 `run/world/session.lock: already locked`，不是端口 —— 
上一轮 `TaskStop` 只杀了 Gradle 任务，**子 JVM 活了下来**，我随后的 RCON 全打到了那个旧进程上（它加载的是旧探针类，
于是我先看到了一堆"旧结果"）。判定与清理方法：`lsof -p <pid> | grep cwd` 看工作目录是不是 `.../GetsKeeper/run`，
然后 `kill <pid>`（本环境 `ps` 被沙箱禁掉，只能靠 lsof 拿 PID）。
